# Contratos requeridos por el frontend para integración backend

Este documento describe las capacidades y datos que el frontend necesita del backend. Todas las llamadas pasan por el API Gateway (`VITE_API_GATEWAY_URL`, R14) con un token Bearer de Firebase Auth (R18). Todos los resultados deben incluir identificador estable, timestamps ISO 8601, estado de dominio y un error tipado cuando corresponda. El backend debe autorizar nuevamente cada operación aunque la UI ya aplique guards.

## Convenciones comunes

- Actor: usuario autenticado y rol efectivo (`STUDENT` o `ADMIN`).
- Moneda: `PEN`; montos decimales no negativos.
- Error: `{ code, message, fieldErrors?, retryable? }`.
- Errores comunes: `FORBIDDEN`, `NOT_PARTICIPANT`, `INVALID_STATE_TRANSITION`, `LISTING_NOT_AVAILABLE`, `OVERLAPPING_RESERVATION`, `PAYMENT_REQUIRED`, `GUARANTEE_REQUIRED`, `LOAN_ALREADY_ACTIVE_CANNOT_CANCEL`, `EXTENSION_PAYMENT_REQUIRED`, `INCIDENT_PENDING`, `PAYMENT_PROVIDER_UNAVAILABLE`.
- `ReservationSnapshot` es inmutable y debe sobrevivir a `COMPLETED`.
- Una transacción referencia explícitamente `reservationId?`, `loanId?` e `incidentId?`; nunca se interpreta un ID como otro tipo de entidad.

## Estados asíncronos

Pagos, garantía, verificación y análisis de evidencias deben permitir `loading`, `success`, `failed` y reintento. El análisis admite `TIMEOUT`/`ERROR`; ninguno puede crear una incidencia, decidir responsabilidad ni bloquear la devolución o la resolución humana.
